Вот практическое руководство по созданию контента уровня с помощью ИИ, без изменения кода.

---

## 1. Общая схема: ИИ пишет бриф, а не движок

Правило проекта: **уровни — это данные**. Движок не должен знать номер главы и не должен содержать хардкодов домов, рельефа или предметов. Поэтому ИИ лучше всего подходит для генерации **брифов** (`src/levels/level-NN.json`) и, при необходимости, правок в генераторе города (`tools/city.js`), но не для правок `src/game.js` или `src/map.js`.

Рекомендуемый цикл:

```
ИИ пишет level-NN.json
        ↓
node tools/build-level.mjs level-NN.json  (валидация + нормализация → level-NN.js)
        ↓
node tools/build-level.mjs --check level-NN.json  (побайтовое совпадение модуля и парсера)
        ↓
python -m http.server 8124 → 3d-game.html?debug=1  (ручная проверка в браузере)
        ↓
ИИ получает скриншот/консоль и правит бриф
```

## 2. Как писать промпты для уровней

### 2.1 Шаблон промпта (бриф)

Всегда начинайте промпт с ссылки на архитектуру и ограничений. Пример заготовки:

> Ты — автор уровня для 3D-шутера на Three.js (ES-модули, без сборщика). Создай JSON-бриф уровня по файлу `src/levels/level-13.json`.
> 
> Ограничения AGENTS.md:
> - Уровень — данные: `kind`, `ground`, `city` (districts, track), `waterways`, `roads`, `buildings`, `gameplay`. Движок не должен знать номер главы.
> - Не хардкодить содержимое уровня в `src/*.js`. В `config.js` только значения по умолчанию.
> - Геометрия детерминирована: сид `city.seed` фиксирует всё; `Math.random` только для разброса монет.
> - `JsonMap` не знает номера главы; 모든 числа — в брифе, а не литералах в модуле.
> - Глава 13 — это `kind: 'json2'` с `city.track` (кольцо-трасса), `relief` (капсульные холмы + пады), `waterways` (`cut`, `wade: false`), `gameplay.goal: 'exit'`.
> - Сообщи мне: 1) готовый JSON-бриф; 2) список потенциальных конфликтов чисел (например, `clearance` vs `grade`, `minRadius` vs фактический радиус дуги); 3) какие автотесты стоит прогнать.

### 2.2 Что указывать ИИ явно, а что оставлять движку

| Явно в брифе (ИИ решает) | Выводится движком/парсером (ИИ не трогает) |
|---|---|
| `kind`, `ground.size/y/color` | Сгенерированный модуль `level-NN.js` |
| `city.seed`, `city.districts[].block`, `street.pitch/width/grade` | Внутренние id домов (`d0_004`, `d1_037`) |
| `city.track.radius/turns/grade/bank/clearance/lamps` | Секция `city` в финальном модуле (убирается парсером) |
| `waterways[].wade`, `bedY`, `surfaceY` | `channels`-запись, `waterwayFoot` |
| `gameplay.goal`, `spawn`, `exit`, `exitRadius`, `enemies.count` | Ассеты, материалы, кэш GLTFLoader |
| `windows.lit`, `clutter.roof.perHouse`, `signage.keep` | Расстановка окон/мусора/вывесок (JsonMap делает сам) |

**Антипаттерн:** просить ИИ прописать в JSON координаты конкретного окна или высоту конкретного этажа дома, которая должна «выглядеть правильно». Это работа движка и генератора; ИИ должен задавать *правила* (рифмы, этажность, сид), а не jednotlivые меши.

### 2.3 Промпт по типам контента

#### Дома (застроенные кварталы)
> Сгенерируй секцию `city.districts[].buildings` для района с `yaw: 18°`. Укажи: `footprint` (L- или U-образный, не выходящий за `block`), `rotation` (кратный 90°, если v1; произвольный, если v2), `height.minFloors/maxFloors`, `roofs.walkable` (true/false), `enterableEvery` (каждый N-й лот вводимый). Не придумывай координаты дверей вручную — задай `door.rect` как правило на ребре комнаты.

#### Ландшафт (рельеф, глава 12-стиль)
> Создай секцию `relief` с 3–5 холмами (капсула: `height · ease(1 − d/radius)`) и 1–2 падами. Убедись, что `hillMaxSlope · 1.5 ≤ maxSlope` (иначе нормализатор выдаст предупреждение). Пад не должен накрывать лот дома, если дом не prévoit настил.

#### Предметы и декор
> Не расставляй предметы вручную. Включи секции `windows` (лит `0.42`), `clutter` (крыши `perHouse: 4`, улицы `every: 26`), `signage` (`keep: 0.7`). JsonMap сам выведет квады и мусор из чисел брифа. Добавь комментарий в metadata, откуда взяты числа (например, подбор по главе 13).

#### Трасса-кольцо (глава 13, `city.track`)
> Сгенерируй `city.track` с `radius: 120`, `turns: 12`, `width: 10`, `grade: 0.08`, `clearance: 3`, `bank: 6`, `lamps: false`, `entries: 2`. Предупреди: `minRadius` — вводящее имя; фактический радиус дуги может быть меньше из-за клампа по `MIN_RUN`. Укажи, какой сид пробовал, и какие отказы генератора posibles (нос вне улицы, кусок < 1 м у окна перил).

## 3. Что можно улучшить в форматах файлов (чтобы ИИ легче генерировал)

Код не меняю, только рекомендации к форматам данных:

### 3.1 JSON Schema «напрямую в брифе»
Добавить в начало `level-NN.json` поле `$schema` или отдельный `.schema.json`, который ИИ может использовать как контекст. Сейчас схема живет в `tools/level-schema.mjs` и неявна для ИИ. Явная схема с описаниями полей уменьшит галлюцинации (например, ИИ не перепутает `grade` у улицы и `grade` у холма).

### 3.2 Именованные константы вместо магических чисел
В брифе сейчас много сырого чисел (`0.12`, `0.08`, `2.63`, `320`). Можно ввести секцию `constants` (или использовать ссылки на `CONFIG` из движка), чтобы ИИ не изобретал свои значения:
```json
"constants": { "trackGrade": 0.08, "trackClearance": 3, "padY": -1.2 }
```
ИИ будет ссылаться на них, а не угадывать.

### 3.3 Алиасы и ссылки (YAML-стиль)
Если формат позволит, полезно было бы ссылаться на один и тот же блок района или шаблон дома из нескольких мест:
```json
"districtTemplate": { "id": "corporate_block", ... },
"districts": [ { "$ref": "corporate_block", "block": {...} } ]
```
Это снизит копипасту и ошибки при массовом генерировании кварталов.

### 3.4 Комментарии в JSON (JSONC) или отдельный `notes.md`
ИИ часто хочет объяснить *почему* выбрано число (например, `spawn: {6.23, -78.47}` — «на стыке двух настилов»). Сейчас комментарии в JSON невозможны. Можно вести рядом `level-NN.notes.md`, куда ИИ пишет rationale. Это помогает при ревью и при повторной генерации того же уровня другим ИИ.

### 3.5 Явные границы «безопасной зоны» для ИИ
Ввести в брифе секцию `aiBoundary`, где автор уровня помечает, что ИИ может менять, а что трогать запрещено (например, `fixed: ["spawn", "exit", "city.seed"]`). Это полезно, когда несколько итераций ИИ правят один уровень.

## 4. Что можно улучшить в движке (описание, без правки кода)

### 4.1 Отладочная панель для валидации ИИ-контента
`src/debug.js` уже рисует `debugIds()` из карты. Можно расширить:
- визуализация `bounds` карты и `solids` (чтобы ИИ видел, зачем `ground.size` не совпадает с руслом);
- отображение открытых/закрытых узлов графа навигации (чтобы ИИ видел, почему враг стоит на месте);
- фотометрия кадра (уже частично есть в планах, но можно вывести на HUD в режиме `?debug=1`).

### 4.2 «Сухой запуск» уровня без рендера
Режим, где `build-level.mjs` или движок считает уровень, но не рендерит — только выдаёт JSON-отчёт: число узлов графа,achable ли точка B, предупреждения парсера, фотометрические пробы. ИИ может прогонять это автоматически, не открывая браузер.

### 4.3 Лучшие сообщения об ошибках нормализатора
Сейчас парсер выбрасывает ошибку с числом. Для ИИ полезнее было бы видеть:
- номер строки в `level-NN.json`;
- какая именно гейт-сравнение не сошлось (например, `amplitude·waves·π ≤ grade·Lmin`);
- предложение, какое число подправить.

### 4.4 Детерминизм для ИИ
Все Generators уже детерминированы сидом. Можно добавить в отчёт от `build-level.mjs` именно те вызовы ГПСЧ, которые сделал генератор, чтобы при изменении сида ИИ мог предсказать, что сдвинется. Сейчас это частично документировано в логах, но не в машиночитаемом виде.

## 5. Рекомендуемый рабочий процесс с ИИ

1. **Запуск.** Промпт с шаблоном выше → получаешь `level-NN.json`.
2. **Сборка.** `node tools/build-level.mjs <путь>`. Если есть ошибки — скопируй текст ошибки обратно в промпт ИИ с просьбой исправить.
3. **Проверка совпадения.** `node tools/build-level.mjs --check <путь>`. Модуль должен совпадать с парсером побайтово.
4. **Браузер.** `python -m http.server 8124` → `http://localhost:8124/3d-game.html?debug=1`. Загрузи главу через отладочную панель. Проверь:
   - враги стоят на опорах (`feetY === groundY`);
   - путь A→B существует (граф связный);
   - нет зелёного «обхода» без полотна, если должен быть обязателен.
5. **Фотометрия.** Если уровень ночной — сделай скриншот и сравни с порогом «улица без огней 40».
6. **Коммит.** `feat: уровень N — описание причины`.

## 6. Пример хорошего промпта (кратко)

```

- 2 района: один с yaw 22°, другой осевой; block 160×160 м.
```

## 1. Статические проверки (Node, до браузера)

### 1.1. Сборка и байт-соответствие
Уже есть `tools/build-level.mjs --check`, но для нового уровня стоит добавить обязательный этап:

- **Два прогона `build-level` подряд дают побайтово одинаковый модуль.** Детерминизм проверяется не только парсером, но и для самого нового брифа.
- **Ноль предупреждений парсера.** Любое предупреждение в собранной главе — сигнал, что геометрия ушла в обходной путь.

### 1.2. Контракт карты (программно)
Новый скрипт, например `tools/check-map-contract.mjs`, который импортирует сгенерированный `level-NN.js` и проверяет:

- все обязательные члены контракта присутствуют: `width`, `depth`, `spawn`, `groundHeightAt`, `isBlocked`, `openPositions`, `worldToNormalized`, `build`, `drawMinimap`, `raySolid`, `resolveSphere`, `rayHitDistance`, `findPath`, `randomNavPoint`, `bounds`, `solids`;
- опциональные члены (`updateStreaming`, `debugIds`) отличаются через `typeof`, а не через `map.kind`;
- `spawn` и `exit` лежат внутри `bounds`;
- `groundHeightAt(spawn.x, spawn.z, 500)` возвращает число, не `NaN`, не `null`;
- `findPath(spawn, exit)` возвращает непустой путь, все узлы пути находятся в `bounds`, длина пути не превышает разумный бюджет (например, не в 10 раз больше прямого расстояния).

### 1.3. Навигация и спавн врагов
- `map.nav.nodes` (если доступен) не пуст; хотя бы `enemies.count × 3` узлов находятся на дистанции `spawnDistance…180` от точки спавна (иначе враги негде возрождать).
- Каждый узел пути A→B стоит на своей опоре: `groundHeightAt(node.x, node.z, 500) ≈ node.y` (для json2/terrain — с допуском шва `J.floorRise`).
- Все узлы графа достижимы от спавна (или хотя бы 99 %) — иначе уровень содержит изолированные карманы.

### 1.4. Бюджет уровня
Для нового уровня можно завести пороги (как для главы 13):

| Показатор | Предлагаемый предел |
|---|---|
| узлов навигации | ≤ 1,5 × решётки (или число, согласованное с владельцем) |
| настилов / пластин | ≤ 300 (или по оценке главы) |
| опор / столбов | ≤ 160 |
| суммарный размер модуля | ≤ 500 КБ (или согласовано) |

Проверка — в `tools/check-new-level.mjs` на этапе сборки.

### 1.5. Атрибуция GLB (если уровень использует внешнюю модель)
- В `README.md` есть строка с лицензией и автором `.glb`;
- В комментарии определения уровня (`metadata` или заголовке JSON) есть автор и лицензия.
Проверка — простой скрипт, ищущий эти строки перед коммитом.

## 2. Браузерные автотесты (запуск из консоли `3d-game.html?debug=1`)

### 2.1. «Дымовый» тест нового уровня
`tests/level-NN.test.js` — экспортирует `runLevelNNTests()`:

1. Загружает главу через `window.game._loadLevel(index)`;
2. Проверяет `window.game.state === 'chapter'`;
3. Проверяет, что `window.game.map` реализует все члены контракта;
4. Проверяет, что консоль браузера не содержала ошибок загрузки (можно собирать `console.error` перед тестом);
5. Проверяет, что все 10 (или `enemies.count + alienEnemies.count`) врагов заспавнены и у каждого `feetY === groundY` (как в исследовании главы 13).

### 2.2. Тест маршрута и прохождения
- `findPath(spawn, exit)` не null;
- кратчайший путь проходит через узлы графа, а не «под землей» (каждый узел пути имеет сопутствующую опору);
- точка B (exit) попадает в узел в пределах `exitRadius` (или `J.navStep`);
- обход без обязательного элемента (кольцо, мост, настил) не существует, если так задумано в данных (как сценарий 9 для главы 13).

### 2.3. Тест жизненного цикла (утечки)
- Перезагрузка главы (`_loadLevel` того же индекса) не увеличивает число мешей в сцене бесконечно;
- после переключения на другую главу и назад старые меши удалены (`dispose` отрабатывает).

### 2.4. Фотометрия (только для ночных уровней)
Если у уровня `sky.lights` или ночной вид:

- рендерить сцену в `WebGLRenderTarget` (`FloatType`);
- читать пиксели `readRenderTargetPixels`;
- проверять пороги: «улица без огней ≥ 40», «под фонарём 80» (или значения, согласованные с владельцем);
- проверять, что летающих огней за камерой нет (пул NightLights не создаёт источников вне координат игрока).

## 3. Регрессионные проверки (при любом новом уровне)

Добавление главы 14 не должно сломать 9–13. Обязательный минимум перед коммитом:

- `node tools/build-level.mjs --check` для **всех** 기존 модулей (09–14) — они должны остаться побайтово прежними;
- `node tools/level-parser.test.mjs` — 120/120;
- все browser-тесты (16 сюит) — 258/259 (или актуальное число с учётом новых тестов);
- новые тесты конкретного уровня — зелёные.

## 4. Пример структуры нового скрипта: `tools/check-new-level.mjs`

Ниже — skeleton (не меняет существующий код, только предлагаемый новый файл):

```js
// tools/check-new-level.mjs
import { readFileSync } from 'fs';
import { fileURLToPath } from 'url';

const levelPath = process.argv[2]; // src/levels/level-14.json
const modulePath = levelPath.replace(/\.json$/, '.js');

// 1. Сборка
// 2. --check (байтовое совпадение)
// 3. Импорт модуля, проверка контракта карты
// 4. Проверка spawn/exit в bounds, groundHeightAt не NaN
// 5. findPath(spawn, exit) не null
// 6. Бюджет узлов / настилов / опор
// 7. Если GLB — проверка атрибуции в README и метаданных
// Выход: process.exitCode = 0 или 1
```

Запуск: `node tools/check-new-level.mjs src/levels/level-14.json`.

Можно добавить в `.husky/pre-commit` или GitHub Actions:
