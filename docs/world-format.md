# Формат данных для процедурной генерации 3D-города

Я бы предложил разработать собственный формат, условно назовём его CityForge.

Его основная задача — не просто хранить готовую 3D-модель города, а описывать город как набор взаимосвязанных сущностей, из которых можно:

- генерировать новые города;
- создавать варианты существующего города с другими параметрами;
- многократно использовать одни и те же модели зданий и объектов;
- изменять здания и объекты индивидуально;
- строить сложные дорожные сети, включая многоуровневые развязки;
- генерировать ландшафт, реки, горы, пещеры;
- загружать город частями;
- использовать данные как для визуализации, так и для игровой логики.

Главная архитектурная идея: отделить описание города от 3D-моделей и от алгоритмов генерации.

Не стоит хранить каждый дом как отдельную геометрическую модель. В данных должно быть описание того, какой это дом, где он расположен, какие у него параметры и на какой шаблон он ссылается. Геометрия при этом хранится отдельно.

Это позволит сделать формат относительно простым, не превращая его в подобие полноценной CAD/BIM-системы.

## 1. Существующие форматы и что из них стоит взять

Полностью изобретать формат не нужно. Уже существуют стандарты, которые покрывают отдельные части задачи.

| Формат        | Для чего предназначен                      | Что полезно взять                                                       |
| ------------- | ------------------------------------------ | ----------------------------------------------------------------------- |
| CityGML 3.0   | Описание семантической 3D-модели города    | Здания, мосты, тоннели, дороги, рельеф, растительность, водоёмы, районы |
| CityJSON      | JSON-представление городской геоинформации | Структуру объектов и геометрию                                          |
| OpenDRIVE     | Описание дорожных сетей                    | Дороги, полосы, соединения, перекрёстки, высоты                         |
| OpenStreetMap | Описание географических объектов           | Узлы, линии, области, отношения между объектами                         |

| 3D Tiles      | Потоковая загрузка больших 3D-сцен         | Пространственное разбиение и LOD                                        |

## 2. Основные принципы CityForge

Я бы заложил семь принципов.

1\. Шаблон и экземпляр — разные сущности.

Шаблон здания описывает общую конструкцию, доступные параметры и 3D-ресурсы. Экземпляр содержит только координаты, поворот, масштаб и индивидуальные настройки.

2\. Генерация и результат генерации разделены.

Город может хранить правила генерации, а не тысячи заранее созданных объектов. При необходимости результат генерации можно сохранить в виде экземпляров.

3\. Геометрия отделена от семантики.

Например, дорога имеет:

- геометрию;
- полосы движения;
- соединения с другими дорогами;
- правила движения;
- материал покрытия;
- визуальное представление.

Это разные характеристики одной сущности.

4\. Город имеет несколько пространственных уровней.

Район → квартал → участок → объект.

При этом дорога или река не обязаны принадлежать одному району: они могут проходить через несколько районов.

5\. Высота — полноценная координата.

Нельзя проектировать дорожную систему только в 2D с последующим добавлением высоты. Нужно изначально поддерживать XYZ и отдельную топологию соединений.

6\. Процедурная генерация должна быть воспроизводимой.

Один и тот же Seed и одна версия генератора должны давать одинаковый результат. Смена одного здания не должна случайным образом менять весь город.

7\. Рендеринг — отдельная задача.

В исходном формате описывается логическая структура города. Меши, коллизии, навигационные сетки, LOD и GPU Instancing могут создаваться при компиляции города.

## 3. Структура данных

Предлагаю следующую иерархию:

City

Система координат, настройки, Seed, размеры города

World

Terrain · Hydrology · Caves

Общий ландшафт и природные объекты

Districts

Районы · Правила · Стили · Плотность

Blocks

Parcels

Участки под застройку

Networks

Roads · Junctions · Railways · Paths

Графы транспортной инфраструктуры

Structures

Buildings · Bridges · Tunnels

Физические сооружения

Instances

Дома · Деревья · Мебель · Освещение · Прочие объекты

Asset Library

3D-модели · Шаблоны · Материалы · Процедурные генераторы

Здесь важно, что `Asset Library` не является частью физического пространства города. Это каталог ресурсов, на которые ссылаются городские сущности.

### 3.1. Корневой объект City

```
{
  "format": "cityforge",
  "version": "0.1",

  "world": {
    "units": "meters",
    "coordinateSystem": {
      "type": "local",
      "handedness": "right",
      "up": "Z"
    },
    "origin": [0, 0, 0],
    "bounds": {
      "min": [0, 0, -100],
      "max": [5000, 5000, 1000]
    }
  },

  "generation": {
    "seed": 123456,
    "generatorVersion": "1.0",
    "deterministic": true
  },

  "assets": {},
  "districts": [],
  "blocks": [],
  "parcels": [],
  "terrain": {},
  "networks": {},
  "structures": [],
  "hydrology": {},
  "caves": {},
  "instances": [],
  "chunks": []
}
```

Почему локальная система координат?

Для игрового города обычно удобнее использовать метры относительно локального начала координат, а не географические широту и долготу. Это уменьшает проблемы точности координат при работе с большими объектами.

При необходимости можно добавить `crs` для связи с реальной географией.

### 3.2. Каталог ресурсов Assets

Это одна из самых важных частей формата.

Нужно поддерживать три типа ресурсов:

| Тип        | Назначение                               |
| ---------- | ---------------------------------------- |
| Prefab     | Готовая 3D-модель                        |
| Procedural | Объект, создаваемый генератором          |
| Composite  | Объект, собранный из нескольких ресурсов |

Пример каталога:

```
{
  "assets": {
    "building.house_01": {
      "kind": "procedural",
      "generator": "building.modular",

      "geometry": {
        "source": "assets/house_01.glb"
      },

      "parameters": {
        "floors": {
          "type": "int",
          "min": 1,
          "max": 4,
          "default": 2
        },
        "roof": {
          "type": "enum",
          "values": ["flat", "gable", "hip"],
          "default": "gable"
        },
        "facade": {
          "type": "enum",
          "values": ["brick", "plaster", "concrete"],
          "default": "plaster"
        }
      },

      "bounds": [12, 10, 15]
    },

    "vegetation.tree_01": {
      "kind": "prefab",
      "geometry": {
        "source": "assets/tree_01.glb"
      }
    },

    "prop.street_lamp": {
      "kind": "prefab",
      "geometry": {
        "source": "assets/street_lamp.glb"
      }
    }
  }
}
```

Пример экземпляра дома:

```
{
  "id": "house_001",
  "template": "building.house_01",

  "transform": {
    "position": [120, 250, 0],
    "rotation": [0, 0, 0, 1],
    "scale": [1, 1, 1]
  },

  "overrides": {
    "floors": 3,
    "roof": "flat",
    "facade": "brick"
  },

  "districtRef": "residential_01",
  "parcelRef": "parcel_105"
}
```

Параметры экземпляра переопределяют значения шаблона.

В результате один шаблон может использоваться для сотен домов с различной этажностью, крышей, фасадом, материалами и другими характеристиками.

Для `Composite` можно предусмотреть составные объекты с дочерними элементами, например автобусная остановка из навеса, скамейки, таблички и осветительного прибора.

Дополнительно я бы предусмотрел `sockets` — точки подключения ресурсов. Например, к дому можно прикреплять кондиционеры, вывески, балконы, антенны и другие компоненты.

### 3.3. Районы Districts

Район — не просто географическая область. Это набор правил, которые определяют, как должен выглядеть и генерироваться его участок города.

Минимальный набор свойств:

| Свойство            | Назначение                                          |
| ------------------- | --------------------------------------------------- |
| `type`              | residential, industrial, commercial, park, downtown |
| `area`              | Географические границы                              |
| `style`             | Архитектурный стиль                                 |
| `buildingDensity`   | Плотность застройки                                 |
| `heightRange`       | Диапазон высоты зданий                              |
| `maxFootprintRatio` | Максимальная доля территории под застройку          |
| `setback`           | Отступ зданий от границ участков                    |
| `buildingPalette`   | Допустимые шаблоны зданий                           |
| `vegetation`        | Правила размещения растений                         |
| `roadStyle`         | Характеристики дорог                                |

Пример:

```
{
  "id": "residential_01",
  "type": "residential",

  "area": {
    "type": "polygon",
    "rings": [
      [
        [0, 0],
        [500, 0],
        [500, 400],
        [0, 400]
      ]
    ]
  },

  "style": "suburban",

  "rules": {
    "buildingDensity": 0.6,
    "heightRange": [6, 18],
    "maxFootprintRatio": 0.4,
    "setback": 3,

    "buildingPalette": [
      {
        "template": "building.house_01",
        "weight": 70,
        "parameterRanges": {
          "floors": [1, 3]
        }
      },
      {
        "template": "building.house_02",
        "weight": 30
      }
    ],

    "vegetation": {
      "density": 0.2,
      "palette": [
        "vegetation.tree_01",
        "vegetation.tree_02"
      ]
    }
  }
}
```

`weight` определяет относительную вероятность выбора шаблона.

Я бы не стал жёстко привязывать все параметры к типу района. Лучше сделать систему профилей и правил, чтобы можно было создавать, например, исторический промышленный район с жилой застройкой или современную коммерческую зону.

При этом для одного района можно поддерживать несколько профилей: например, разные архитектурные стили для центральной части и периферии.

### 3.4. Кварталы и участки

Я бы не ограничивался районами.

Для реалистичной генерации города полезно ввести два дополнительных уровня:

- `Block` — квартал, ограниченный дорогами или другими границами.
- `Parcel` — отдельный земельный участок, на котором может находиться здание.

Например:

```
{
  "blocks": [
    {
      "id": "block_001",
      "districtRef": "residential_01",
      "area": {
        "type": "polygon",
        "rings": [
          [[100, 100], [200, 100], [200, 200], [100, 200]]
        ]
      },
      "parcels": [
        "parcel_001",
        "parcel_002"
      ]
    }
  ],

  "parcels": [
    {
      "id": "parcel_001",
      "blockRef": "block_001",
      "area": {
        "type": "polygon",
        "rings": [
          [[100, 100], [150, 100], [150, 150], [100, 150]]
        ]
      },
      "buildable": true,
      "buildingRules": {
        "maxFloors": 3
      }
    }
  ]
}
```

Это позволит реализовать разные алгоритмы генерации:

1. Генерация дорожной сети.
2. Формирование кварталов между дорогами.
3. Разделение кварталов на участки.
4. Размещение зданий внутри участков.
5. Генерация элементов окружения.

Необязательно всегда хранить все кварталы и участки. Их можно генерировать автоматически и сохранять только тогда, когда необходимо зафиксировать конкретный результат.

## 4. Дорожная сеть Networks

Это самая сложная часть формата, особенно из-за многоуровневых развязок.

Я бы использовал графовую модель.

Она состоит из трёх основных сущностей:

- `RoadNode` — узел дорожной сети.
- `RoadSegment` — отрезок дороги между двумя узлами.
- `Junction` — перекрёсток или сложное соединение дорожных сегментов.

### 4.1. RoadNode

```
{
  "id": "node_001",
  "position": [100, 200, 0],
  "layer": "ground"
}
```

`position` — XYZ в мировых координатах.

`layer` — логический уровень дорожной сети. Например:

- `ground` — уровень земли;
- `bridge_01` — первый уровень эстакады;
- `bridge_02` — второй уровень;
- `underground` — подземная дорога.

Важно: `layer` не определяет физическую высоту. Она задаётся координатой Z. Это метка для организации топологии.

### 4.2. RoadSegment

Дорожный сегмент задаёт геометрию и характеристики дороги.

```
{
  "id": "road_001",

  "from": "node_001",
  "to": "node_002",

  "type": "arterial",
  "layer": "ground",

  "path": [
    [100, 200, 0],
    [150, 200, 0],
    [200, 210, 0]
  ],

  "lanes": [
    {
      "id": "lane_01",
      "direction": "forward",
      "width": 3.5,
      "type": "vehicle"
    },
    {
      "id": "lane_02",
      "direction": "backward",
      "width": 3.5,
      "type": "vehicle"
    }
  ],

  "shoulderWidth": 1.0,
  "sidewalk": true,

  "surface": "asphalt",
  "speedLimit": 60
}
```

Здесь `path` — опорная линия дороги. По ней впоследствии строится дорожное полотно.

В дальнейшем можно расширить формат кривыми Безье или другими типами сплайнов. Для первой версии полилинии достаточно.

Полосы лучше хранить отдельно, а не просто задавать `laneCount`. Это даст возможность описывать:

- полосы с разным направлением;
- выделенные автобусные полосы;
- трамвайные пути;
- велодорожки;
- полосы разгона и торможения;
- полосы поворота.

Тротуары можно хранить как автоматически генерируемые элементы RoadSegment, а сложные тротуарные пространства — как отдельные сегменты пешеходной сети.

### 4.3. Junction

Обычного соединения дорожных линий недостаточно. Нужно также описывать допустимые перемещения между полосами.

```
{
  "id": "junction_001",

  "connections": [
    {
      "from": {
        "segment": "road_001",
        "lane": "lane_01",
        "end": "to"
      },

      "to": {
        "segment": "road_002",
        "lane": "lane_03",
        "end": "from"
      },

      "movement": "straight"
    }
  ],

  "type": "signalized"
}
```

Это позволит в будущем реализовать:

- светофоры;
- правила поворотов;
- односторонние дороги;
- движение транспорта;
- запрет определённых манёвров;
- перестроения между полосами.

### 4.4. Многоуровневые развязки и мосты

Здесь предлагаю важное разделение: дорожная сеть описывает движение, а мост — физическое сооружение.

То есть мост не должен сам по себе заменять дорожный сегмент.

Например, есть обычная дорога на высоте 0 и эстакада на высоте 12 метров. Они пересекаются в проекции сверху, но не соединены.

В графе у них разные узлы, и пересечение координат не создаёт соединения автоматически.

[wevolver.com](https://www.wevolver.com/article/high-speed-data-and-connected-cars?utm_source=chatgpt.com)

Мост описывается отдельно:

```
{
  "id": "bridge_001",
  "type": "bridge",
  "template": "bridge.concrete_viaduct",

  "decks": [
    {
      "id": "deck_upper",
      "roadRefs": ["road_010"],
      "clearance": 8.0
    }
  ],

  "parameters": {
    "pierSpacing": 25,
    "railings": true,
    "supports": "auto"
  }
}
```

При этом `road_010` содержит всю информацию о геометрии и полосах движения по мосту.

В случае двухэтажного моста можно добавить два элемента в `decks`, каждый со своими дорожными сегментами.

Для эстакад и сложных развязок дополнительно понадобятся:

- `ramp` — съезды и заезды;
- `merge` — слияние потоков;
- `split` — разделение потоков;
- `connector` — соединительный участок;
- `clearance` — минимальный вертикальный габарит;
- `supportPoints` — точки размещения опор.

Пандусы должны быть обычными дорожными сегментами с изменяющейся высотой, а не отдельным типом физического моста.

Аналогичным образом можно описывать тоннели:

```
{
  "id": "tunnel_001",
  "type": "tunnel",
  "template": "tunnel.rock",

  "roadRefs": ["road_020"],

  "portals": [
    {
      "id": "portal_start",
      "position": [100, 200, -10]
    },
    {
      "id": "portal_end",
      "position": [400, 200, -10]
    }
  ],

  "parameters": {
    "lining": "concrete",
    "lighting": true
  }
}
```

Для тоннелей дорожная сеть остаётся непрерывной, а физическое сооружение отвечает за стены, свод, порталы и другие элементы.

Такую модель удобно использовать и для обычных автомобильных дорог, и для метро, железных дорог, пешеходных переходов.

## 5. Природная среда

Для природных объектов я бы не пытался использовать единую модель геометрии. У рельефа, рек и пещер разные требования.

### 5.1. Terrain — рельеф

Нужно поддерживать несколько способов представления ландшафта:

| Представление | Применение                                |
| ------------- | ----------------------------------------- |
| Heightmap     | Обычный рельеф, холмы и равнины           |
| TIN / Mesh    | Скалы, крутые склоны, сложные поверхности |
| Procedural    | Генерация гор, долин и других форм        |
| Voxel / SDF   | Пещеры, полости, нависающие участки       |

Я бы сделал базовый рельеф в виде Heightmap, а сложные элементы — в виде модификаторов.

Например:

```
{
  "terrain": {
    "base": {
      "type": "heightfield",
      "source": "terrain/base.bin",
      "resolution": 2
    },

    "modifiers": [
      {
        "id": "mountain_001",
        "type": "mountain",
        "center": [1000, 1200],
        "radius": 300,
        "height": 150,
        "falloff": "smooth"
      },
      {
        "id": "valley_001",
        "type": "valley",
        "path": [
          [100, 100],
          [300, 250],
          [500, 400]
        ],
        "width": 50,
        "depth": 20
      }
    ]
  }
}
```

Модификаторы можно применять последовательно:

1. Создание базового рельефа.
2. Формирование гор.
3. Формирование долин.
4. Создание берегов и русел.
5. Применение локальных изменений.

Для крупных территорий рельеф желательно разбить на тайлы (Terrain Chunks).

Высокую точность на склонах, скалах и в местах нависающей геометрии обеспечивать только Heightmap не сможет. Там потребуется дополнительная геометрия или объёмное представление.

### 5.2. Hydrology — реки и водоёмы

Река должна быть самостоятельной сущностью, а не просто объектом с мешем.

```
{
  "hydrology": {
    "rivers": [
      {
        "id": "river_001",

        "path": [
          [100, 100, 20],
          [200, 150, 18],
          [300, 250, 15],
          [400, 400, 10]
        ],

        "width": 15,
        "depth": 4,

        "flow": "start_to_end",
        "carveTerrain": true
      }
    ],

    "lakes": [
      {
        "id": "lake_001",

        "area": {
          "type": "polygon",
          "rings": [
            [
              [500, 500],
              [700, 500],
              [700, 650],
              [500, 650]
            ]
          ]
        },

        "waterLevel": 12
      }
    ]
  }
}
```

Что ещё можно добавить:

- изменение ширины реки по длине;
- скорость и направление течения;
- глубину русла;
- тип береговой линии;
- пороги и водопады;
- сезонное изменение уровня воды;
- связь рек друг с другом;
- точки впадения и истоки.

Особенно важно, чтобы река могла влиять на рельеф. При генерации нужно учитывать русло, берега, глубину и уровень воды.

### 5.3. Caves — пещеры

Пещеры лучше описывать не только геометрией, но и структурой полостей.

Предлагаю три основные сущности:

- `Chamber` — помещение или камера.
- `Passage` — тоннель между камерами.
- `Entrance` — выход на поверхность.

Пример:

```
{
  "caves": {
    "systems": [
      {
        "id": "cave_001",

        "chambers": [
          {
            "id": "chamber_001",
            "center": [100, 200, -30],
            "radius": [15, 20, 8]
          },
          {
            "id": "chamber_002",
            "center": [200, 250, -45],
            "radius": [25, 20, 10]
          }
        ],

        "passages": [
          {
            "id": "passage_001",
            "from": "chamber_001",
            "to": "chamber_002",
            "path": [
              [100, 200, -30],
              [150, 220, -35],
              [200, 250, -45]
            ],
            "radius": 4
          }
        ],

        "entrances": [
          {
            "id": "entrance_001",
            "chamberRef": "chamber_001",
            "surfacePosition": [100, 200, 0],
            "openingRadius": 3
          }
        ]
      }
    ]
  }
}
```

Это логическое описание. Система генерации на его основании создаёт объёмную геометрию пещер.

Для сложных пещер можно хранить дополнительное представление в виде SDF или воксельного ресурса. Например, чтобы делать не только тоннели, но и неровные залы, сталактиты, полости и подземные водоёмы.

Важно, чтобы пещера могла пересекаться с тоннелем или шахтой и имела связь с поверхностью.

## 6. Дополнительные игровые объекты

Я бы предусмотрел универсальный механизм `Instances`, который позволяет размещать любые ресурсы, не вводя отдельный раздел для каждого типа объекта.

Например, можно хранить:

- здания;
- деревья, кустарники, траву;
- фонари и дорожные знаки;
- остановки;
- скамейки и урны;
- рекламные конструкции;
- ограждения;
- памятники;
- автомобили как статические объекты;
- игровые объекты, с которыми можно взаимодействовать.

Различие между экземпляром дома и экземпляром дерева заключается преимущественно в шаблоне и дополнительных параметрах.

Однако есть отдельные типы, которым нужны собственные подсистемы:

| Подсистема      | Что описывает                                 |
| --------------- | --------------------------------------------- |
| Vegetation      | Массовое размещение растительности            |
| StreetFurniture | Городское оборудование                        |
| TrafficControl  | Светофоры, знаки, разметка                    |
| Lighting        | Уличное освещение                             |
| Navigation      | Проходимость и навигация                      |
| Utilities       | Водоснабжение, электроснабжение, канализация  |
| Transit         | Остановки и маршруты общественного транспорта |

Не нужно реализовывать все эти подсистемы в первой версии. Их можно подключить через расширения.

Особенно рекомендую предусмотреть отдельное описание поведения объекта:

```
{
  "id": "lamp_001",
  "template": "prop.street_lamp",

  "transform": {
    "position": [100, 200, 0],
    "rotation": [0, 0, 0, 1],
    "scale": [1, 1, 1]
  },

  "gameplay": {
    "interactable": false,
    "collision": true
  },

  "properties": {
    "lightIntensity": 1.5,
    "enabledAtNight": true
  }
}
```

Это позволит отделить внешний вид объекта от игровой логики.

## 7. Процедурная генерация

На мой взгляд, именно здесь формат должен отличаться от обычного формата хранения 3D-моделей городов.

Я предлагаю предусмотреть три режима создания объектов.

Режим 1

Procedural generation

Объекты создаются автоматически по правилам района, квартала или участка.

[esri.github.io](https://esri.github.io/cityengine/vitruvio?utm_source=chatgpt.com)

Например, генерация жилого квартала с заданной плотностью и архитектурным стилем.

Режим 2

Готовые ресурсы размещаются в определённых координатах с заданными параметрами.

[Farmhouse Pack for Unreal Engine — Christopher Albeluhn](https://images.openai.com/static-rsc-4/N4lzNXArMuNO7LRlzSo2ImjPASnyDjx2QTdkOhXOUe1bnlj05vK-H9cOBRQ8HzTdeEy0W3VCy5y26-vYOt3IVnrOLC41FVmMyhZ4isu6h5B-xbumst8yOK_nRiemSTujmQHe6IyM4nrBpkxEbJFqZDHX9nduOOE5cEq6xHTkwcM?purpose=inline)

Например, генерация обычной застройки вокруг вручную созданного центра города.

### 7.1. Генерация с учётом Seed

Здесь есть важный технический момент.

Не рекомендую использовать один глобальный генератор случайных чисел для всего города.

Лучше рассчитывать локальный Seed по стабильным идентификаторам:

```
citySeed
    + districtId
    + blockId
    + parcelId
    + generatorVersion
```

Тогда изменение одного района не приведёт к случайному изменению всех остальных районов.

Для генерации объектов стоит предусмотреть:

```
{
  "id": "house_generated_001",
  "template": "building.house_01",

  "generation": {
    "source": "procedural",
    "seed": 84521,
    "generator": "building.modular",
    "generatorVersion": "1.2"
  },

  "locked": false
}
```

`locked: true` означает, что объект нельзя изменять при повторной генерации.

Это важно для редактора города: разработчик может автоматически создать район, а затем вручную заменить несколько зданий и зафиксировать их.

### 7.2. Правила генерации должны быть независимыми от алгоритмов

Например, район может определять:

```
{
  "buildingDensity": 0.7,
  "buildingPalette": [
    {
      "template": "building.house_01",
      "weight": 60
    },
    {
      "template": "building.house_02",
      "weight": 40
    }
  ]
}
```

Но он не должен содержать код, который непосредственно размещает здания.

Вместо этого генератор `building.urban@1.0` получает:

- границы района;
- кварталы;
- участки;
- правила застройки;
- доступные шаблоны;
- Seed.

И возвращает набор экземпляров.

Так можно будет заменять алгоритмы генерации, не меняя сами данные города.

## 8. Пространственное разбиение Chunk

Для большого города необходимо предусмотреть загрузку по частям.

Не стоит загружать все объекты одновременно.

Предлагаю ввести `Chunk` — пространственную область, содержащую ссылки на расположенные в ней объекты и ресурсы.

```
{
  "chunks": [
    {
      "id": "chunk_0_0",

      "bounds": {
        "min": [0, 0, -100],
        "max": [500, 500, 300]
      },

      "file": "chunks/chunk_0_0.json"
    },
    {
      "id": "chunk_1_0",

      "bounds": {
        "min": [500, 0, -100],
        "max": [1000, 500, 300]
      },

      "file": "chunks/chunk_1_0.json"
    }
  ]
}
```

Примерный размер Chunk можно выбрать 256 × 256 или 512 × 512 метров, но окончательное значение зависит от масштаба игры и производительности.

При этом нужно учесть:

- здание принадлежит одному Chunk по координате опорной точки;
- дорога может проходить через несколько Chunk;
- крупные объекты могут пересекать границы;
- ссылки на общие ресурсы не должны дублировать сами 3D-модели;
- общие узлы дорожного графа должны сохранять идентификаторы между соседними Chunk.

В перспективе можно использовать LOD для объектов и целых районов.

Например:

- LOD0 — полноценные здания с детализацией;
- LOD1 — упрощённые здания;
- LOD2 — упрощённая геометрия района;
- LOD3 — визуальное представление города издалека.

Здесь пригодится идея 3D Tiles: иерархическое разбиение сцены и загрузка по пространственным уровням. Сам стандарт рассчитан в том числе на большие наборы зданий, экземпляров и фотограмметрии.&#x20;

## 9. Что ещё стоит предусмотреть

Есть несколько вещей, о которых легко забыть при проектировании подобного формата.

| Возможность         | Почему полезна                         | Приоритет           |
| ------------------- | -------------------------------------- | ------------------- |
| PedestrianNetwork   | Пешеходные дорожки, переходы, лестницы | Высокий             |
| RailwayNetwork      | Железные дороги и трамвайные пути      | Средний             |
| Parking             | Парковочные места и парковки           | Средний             |
| TrafficControl      | Светофоры, знаки, разметка             | Высокий             |
| BuildingInterior    | Интерьеры и этажи зданий               | Средний             |
| Collision           | Физические столкновения                | Высокий             |
| Navigation          | Навигация NPC и транспорта             | Высокий             |
| VegetationScatter   | Массовое размещение растений           | Высокий             |
| DestructibleObjects | Разрушаемые объекты                    | По требованиям игры |
| WeatherZones        | Локальные погодные условия             | Низкий              |
| SoundZones          | Звуковые зоны                          | Низкий              |
| UtilityNetworks     | Электричество, вода, канализация       | По требованиям игры |

Особенно я бы обратил внимание на три вещи.

Интерьеры. Даже если сейчас они не нужны, стоит оставить возможность размещать помещения внутри зданий. У здания могут быть этажи, лестницы, лифты, помещения и точки входа.

Навигация. Не нужно привязывать навигацию исключительно к дорогам. NPC могут перемещаться по тротуарам, лестницам, мостам, тоннелям, зданиям и природным объектам.

Взаимодействие с рельефом. Дороги, здания, мосты и реки должны учитывать рельеф, а не существовать независимо от него.

Например, при размещении дома может понадобиться выравнивание площадки, а при создании дороги в горах — выемка грунта или формирование насыпи.

Для этого полезно иметь универсальный механизм модификации Terrain:

```
{
  "id": "road_cut_001",
  "type": "terrain_modifier",
  "sourceRef": "road_001",
  "operation": "subtract",
  "parameters": {
    "width": 12,
    "depth": 5,
    "falloff": 3
  }
}
```

## 10. Рекомендуемая структура файлов

Для физического хранения я бы не делал один огромный JSON-файл.

Предлагаю следующую структуру:

```
city/
├── city.json                  # Главный манифест города
│
├── assets/
│   ├── buildings/
│   ├── bridges/
│   ├── roads/
│   ├── vegetation/
│   ├── props/
│   └── materials/
│
├── districts/
│   ├── residential.json
│   ├── industrial.json
│   └── downtown.json
│
├── networks/
│   ├── roads.json
│   ├── pedestrian.json
│   ├── railways.json
│   └── junctions.json
│
├── terrain/
│   ├── terrain.json
│   ├── heightmaps/
│   └── volumes/
│
├── hydrology/
│   ├── rivers.json
│   └── lakes.json
│
├── structures/
│   ├── bridges.json
│   └── tunnels.json
│
├── chunks/
│   ├── chunk_0_0.json
│   ├── chunk_0_1.json
│   └── chunk_1_0.json
│
└── generated/
    ├── meshes/
    ├── collisions/
    ├── navigation/
    └── lod/
```

Это логическая структура. Физически некоторые файлы можно объединять.

### Форматы хранения

Я бы использовал следующее сочетание:

| Данные                        | Формат                            |
| ----------------------------- | --------------------------------- |
| Основное описание города      | JSON                              |
| Правила процедурной генерации | JSON                              |
| 3D-модели                     | glTF / GLB                        |
| Материалы                     | glTF или отдельные ресурсы движка |
| Heightmap                     | Бинарный массив или текстура      |
| Сложный рельеф                | Mesh / бинарная геометрия         |
| Пещеры                        | SDF / Voxel / Mesh                |
| Результаты генерации          | Бинарные Chunk-файлы              |

JSON удобен для разработки, редактирования и генерации данных. Но не нужно использовать его для хранения миллионов вершин и экземпляров растительности.

Впоследствии можно добавить компиляцию исходного описания в оптимизированный игровой формат.

## 11. Что взять из существующих форматов

Теперь несколько важных уточнений по существующим стандартам.

CityJSON — наиболее близкий кандидат на основу.

На ноябрь 2026 года актуальная опубликованная спецификация — CityJSON 2.0.2. Это официальный стандарт OGC, JSON-представление подмножества модели CityGML 3.0. Он поддерживает городские объекты, их атрибуты, связи и повторное использование геометрических шаблонов.&#x20;

CityJSON+2

OpenDRIVE я бы использовал как ориентир для дорожной подсистемы. Особенно интересна модель, в которой дороги описываются относительно опорной линии, а полосы и профили высот привязываются к ней.&#x20;

## 13. Итоговая архитектура

Я бы остановился на следующем устройстве:

CityForge — Source Data

JSON: город, объекты, связи, правила, Seed

City Generator

Генерация районов, кварталов, дорог, зданий, рельефа

City Compiler

Проверка, оптимизация, LOD, коллизии, навигация, Chunk

Game Engine

Загрузка и отображение города, игровая логика, симуляция

Моя главная рекомендация: не делать CityForge просто форматом хранения 3D-объектов. Сделать его форматом описания и генерации городской среды.

Тогда он сможет использоваться не только для одного города, но и для целого набора процедурно генерируемых городов, каждый из которых будет иметь собственную структуру, архитектуру, инфраструктуру и природную среду.

При этом CityJSON можно использовать для обмена семантическими городскими данными, OpenDRIVE — для импорта и экспорта дорожных сетей, GLB — для ресурсов.

Такой подход даст достаточно простой исходный формат, но не заставит переписывать архитектуру, когда появятся сложные развязки, пещеры, подземная инфраструктура и потоковая загрузка.







что если нужно сделать частичную загрузку карты по чанкам, как тогда быть, для каждого чанка делать свой json? как быть с реками и дорогами? что если дом приходится на границу чанков?


Я бы сделал не город, состоящий из независимых JSON-файлов, а единую логическую модель города, которая при сборке автоматически разбивается на чанки.

Это принципиальное различие.

Дорога, река или здание должны оставаться одной логической сущностью, даже если их геометрия находится в нескольких чанках.

Чанк в этой архитектуре — единица хранения, загрузки и выгрузки данных, а не обязательная граница существования объекта.

## 1. Разделить три уровня данных

Предлагаю такую архитектуру:

Уровень 1. Source Data — исходные данные города

Полные описания районов, зданий, дорог, рек, ландшафта. У каждой сущности свой глобальный ID.

City Compiler

Уровень 2. Chunk Data — данные пространственных фрагментов

Геометрия, попавшая в конкретные чанки, ссылки на объекты, граничные соединения.

Уровень 3. Runtime — игровое представление

Загрузка, отображение, коллизии, навигация, выгрузка и кэширование.

Например, река в исходных данных одна. При компиляции она разбивается на фрагменты по чанкам. В игре загружаются только фрагменты рек из нужной области.

Это позволяет не усложнять исходный формат из-за особенностей потоковой загрузки.

Для прототипа можно вообще оставить JSON вместо бинарных файлов. Позже заменить сериализацию на бинарную, не меняя логическую модель.

Я бы не рекомендовал вручную редактировать данные каждого чанка. Они должны генерироваться компилятором из исходной модели.

## 3. Как организовать индексацию чанков

Предлагаю регулярную сетку с фиксированным размером.

Например, размер чанка — 256 × 256 метров.

### Пример пространственной сетки

Условная сетка с координатами чанков. Выделенный чанк — пример активной области.

Координаты чанка вычисляются из мировых координат:

```
chunkX = floor((worldX - originX) / chunkSize)
chunkY = floor((worldY - originY) / chunkSize)
```

Таким образом, например, точка `[520, 300]` при размере 256 метров относится к чанку `2_1`, если начало координат равно `[0, 0]`.

Идентификатор чанка:

```
chunk_2_1
```

В `city.json`:

```
{
  "format": "cityforge",
  "version": "0.2",

  "world": {
    "origin": [0, 0, 0],
    "units": "meters"
  },

  "streaming": {
    "scheme": "grid",
    "chunkSize": [256, 256],
    "verticalSize": null
  },

  "compiledIndex": "compiled/chunk-index.json"
}
```

Я бы начал с двумерной сетки. Высота Z остаётся полноценной координатой объектов, но не требует немедленного введения третьего индекса чанков. Для вертикально сложного города можно позже добавить пространственные слои.

## 4. Как хранить объекты, пересекающие границы чанков

Здесь я предлагаю ввести два понятия:

- `homeChunk` — чанк, которому принадлежит объект;
- `coverageChunks` — все чанки, геометрическую область которых объект пересекает.

Это позволит избежать дублирования объектов.

### Пример: дом пересекает границу

### Дом на границе двух чанков

Схематично: дом физически пересекает границу, но остаётся одним объектом.

Не нужно создавать два дома или разрезать обычный дом на две независимые модели.

Можно сделать так:

```
{
  "id": "house_001",
  "template": "building.house_01",

  "homeChunk": "chunk_0_0",

  "coverageChunks": [
    "chunk_0_0",
    "chunk_1_0"
  ],

  "transform": {
    "position": [145, 100, 0],
    "rotation": [0, 0, 0, 1],
    "scale": [1, 1, 1]
  },

  "bounds": {
    "min": [130, 90, 0],
    "max": [175, 120, 15]
  }
}
```

Правила:

1. Полное описание здания существует в одном экземпляре.
2. За объект отвечает один `homeChunk`.
3. Остальные чанки содержат только ссылку на объект.
4. При загрузке нескольких чанков движок не создаёт повторные экземпляры здания.
5. Объект выгружается, только когда ни один активный чанк больше не нуждается в нём.

Последний пункт очень важен.

Допустим, игрок находится в `chunk_1_0`, а дом частично выступает из `chunk_0_0`. Несмотря на то что дом принадлежит первому чанку по правилу `homeChunk`, его необходимо отобразить.

Поэтому система загрузки должна учитывать `coverageChunks`, а не только принадлежность объекта.

Для обычных зданий я рекомендую именно такую модель. Разрезать геометрию здания между чанками не нужно: это усложнит освещение, коллизии, интерьеры и выгрузку.

Для действительно больших сооружений — стадионов, торговых центров, заводских комплексов — можно предусмотреть отдельное разбиение геометрии на части. Но логически они всё равно будут одним объектом с одним ID.

## 5. Что делать с дорогами

С дорогами ситуация другая.

Дорога может протягиваться через десятки чанков. Загружать всю её геометрию при загрузке одного чанка нерационально.

Здесь нужно разделить:

- логическую дорогу;
- топологию дорожной сети;
- геометрические фрагменты дороги.

### 5.1. Логическая дорога

В исходной модели она хранится целиком:

```
{
  "id": "road_001",
  "type": "highway",

  "path": [
    [100, 100, 0],
    [250, 100, 0],
    [400, 120, 5],
    [600, 200, 10],
    [900, 250, 10]
  ],

  "width": 14,

  "surface": "asphalt",
  "speedLimit": 90,

  "networkRefs": [
    "node_001",
    "node_002"
  ]
}
```

Это исходное описание, которое не зависит от чанков.

### 5.2. Геометрические фрагменты

При компиляции дорога разрезается на фрагменты по границам чанков.

### Одна дорога — три геометрических фрагмента

Все три части являются продолжением одной и той же дороги.

В каждом чанке будет находиться только соответствующий участок дорожной геометрии.

Например:

```
{
  "chunkId": "chunk_0_0",

  "roadFragments": [
    {
      "id": "road_001_part_0",
      "roadRef": "road_001",

      "range": [0.0, 0.3],

      "fromPortal": null,
      "toPortal": "portal_road_001_a"
    }
  ]
}
```

Следующий чанк:

```
{
  "chunkId": "chunk_1_0",

  "roadFragments": [
    {
      "id": "road_001_part_1",
      "roadRef": "road_001",

      "range": [0.3, 0.7],

      "fromPortal": "portal_road_001_a",
      "toPortal": "portal_road_001_b"
    }
  ]
}
```

И третий:

```
{
  "chunkId": "chunk_2_0",

  "roadFragments": [
    {
      "id": "road_001_part_2",
      "roadRef": "road_001",

      "range": [0.7, 1.0],

      "fromPortal": "portal_road_001_b",
      "toPortal": null
    }
  ]
}
```

Здесь `range` — условный диапазон вдоль опорной линии дороги, нормализованный от 0 до 1. В реальной реализации лучше хранить также точные расстояния вдоль линии (`sStart`, `sEnd`).

### 5.3. Что такое Portal

Я предлагаю ввести универсальную сущность `Portal`.

Это точка соединения между фрагментами пространственных объектов, находящихся в соседних чанках.

```
{
  "id": "portal_road_001_a",

  "position": [256, 48, 3],

  "networkRef": "road_network_001",

  "roadRef": "road_001",

  "layer": "ground",

  "tangent": [0.95, 0.2, 0]
}
```

Portal фиксирует:

- точную позицию соединения;
- принадлежность к объекту;
- направление продолжения;
- уровень дороги;
- идентификатор соединения.

В соседнем чанке используется тот же идентификатор Portal.

Это позволяет гарантировать, что при загрузке соседних чанков дорожные фрагменты соединятся корректно.

Важное уточнение: Portal на границе чанка не является обычным перекрёстком. Он обозначает продолжение одной сущности. Движение между дорогами должно определяться графом дорожной сети и Junction.

Для многоуровневых дорог обязательно учитывать Z и `layer`, иначе пересекающиеся в проекции дороги могут ошибочно соединиться.

## 6. Что делать с реками

Реки по принципу разбиения похожи на дороги, но имеют дополнительные требования.

Исходная река остаётся одной сущностью:

```
{
  "id": "river_001",

  "path": [
    [100, 100, 30],
    [300, 150, 25],
    [500, 300, 18],
    [800, 400, 10]
  ],

  "widthProfile": [
    [0, 10],
    [0.5, 20],
    [1, 35]
  ],

  "flowDirection": "start_to_end",
  "waterLevelMode": "profile"
}
```

При компиляции она разрезается на речные фрагменты.

Но здесь нужно сохранить не только геометрию, но и непрерывность:

- ширины русла;
- высоты поверхности воды;
- береговой линии;
- направления течения;
- параметров материала;
- текстурных координат.

Например, текстура воды не должна начинаться заново на каждой границе чанка. Иначе появятся заметные визуальные разрывы.

Поэтому у реки должен быть глобальный параметр расстояния вдоль русла, условно `s`.

Каждый фрагмент использует исходные значения `s`, а не начинает отсчёт с нуля.

### Важный момент: береговая линия

Если река генерируется как полигон или меш, одного разбиения центральной линии недостаточно.

Компилятор должен:

1. Построить полную геометрию русла и берегов.
2. Разрезать её по границам чанков.
3. Сохранить одинаковые координаты вершин на общих границах.
4. Не допустить наложения или появления щелей.

Иначе можно получить ситуацию, когда сама линия реки непрерывна, а вода между чанками имеет видимые разрывы.

Для озёр можно использовать аналогичный принцип: одна логическая сущность озера, но несколько геометрических фрагментов, если оно занимает несколько чанков.

## 7. А что с рельефом?

Для рельефа я бы применил именно тайловую модель.

В отличие от домов, Terrain изначально является большим непрерывным объектом, который удобно хранить отдельными тайлами.

Например:

```
terrain/
├── tile_0_0.bin
├── tile_0_1.bin
├── tile_1_0.bin
└── tile_1_1.bin
```

Каждый тайл хранит собственную Heightmap и параметры материала.

Но есть обязательное условие: соседние тайлы должны иметь абсолютно одинаковые значения высоты на общей границе.

Например, если последний столбец высот первого тайла имеет значения:

```
[10.0, 12.5, 14.0, 13.2]
```

то первый столбец следующего тайла должен содержать те же значения.

Дополнительно рекомендую использовать один или несколько пограничных рядов данных (`border samples` / `ghost cells`). Они нужны для расчёта нормалей, сглаживания и смешивания материалов около границ.

Для гор, скал и пещер, имеющих сложную объёмную геометрию, можно использовать отдельные геометрические фрагменты в разных чанках.

| Дерево         | Не разбивается                                                     | По точке размещения                                 |
| Мебель         | Не разбивается                                                     | По точке размещения                                 |
| Большое здание | При необходимости делится на геометрические части                  | Один логический владелец                            |
| Дорога         | Разбивается на фрагменты                                           | По пересечению с чанками                            |
| Река           | Разбивается на фрагменты                                           | По пересечению с чанками                            |
| Мост           | Может разбиваться на части                                         | Один логический владелец                            |
| Тоннель        | Разбивается на фрагменты                                           | По пересечению с чанками                            |
| Ландшафт       | Тайловая структура                                                 | По сетке                                            |

| Квартал        | Обычно целиком, при необходимости фрагменты                        | По геометрии                                        |
| Пещера         | По камерам и участкам тоннелей                                     | По пересечению с чанками                            |

Для определения пересечения лучше использовать не только координату центра объекта, но и его bounding box (AABB).

Например:

```
Object:
    position = [250, 200, 0]
    bounds = [230, 180, 0] -> [280, 220, 20]

Chunk:
    bounds = [0, 0, -100] -> [256, 256, 300]

Result:
    object intersects chunk
```

Для объектов, расположенных точно на границе, нужно зафиксировать единое правило: например, владение определяется по опорной точке в полуоткрытом диапазоне координат `[min, max)`. Это предотвращает ситуацию, когда два чанка считают один и тот же объект своим.

## 9. Как должен выглядеть Chunk Index

Я бы обязательно ввёл отдельный индекс всех чанков.

Он позволяет определить, что требуется загрузить, не читая содержимое всех файлов.

Например:

```
{
  "version": "1.0",

  "chunks": {
    "chunk_0_0": {
      "bounds": {
        "min": [0, 0, -100],
        "max": [256, 256, 500]
      },

      "neighbors": [
        "chunk_0_1",
        "chunk_1_0"
      ],

      "files": {
        "terrain": "chunks/0_0/terrain.bin",
        "roads": "chunks/0_0/roads.bin",
        "water": "chunks/0_0/water.bin",
        "instances": "chunks/0_0/instances.bin"
      },

      "entities": [
        "house_001",
        "house_002",
        "river_001",
        "road_001"
      ]
    }
  }
}
```

Но я бы ещё немного усовершенствовал эту структуру:

- `entities` — логические сущности, пересекающие чанк;
- `fragments` — геометрические части этих сущностей, находящиеся непосредственно в чанке;
- `portals` — соединения с соседними чанками;
- `dependencies` — дополнительные ресурсы, необходимые для загрузки;
- `lod` — доступные уровни детализации.

Например, дорога `road_001` может встречаться в `entities` нескольких чанков, но каждый чанк хранит свой собственный фрагмент.

## 10. Как будет работать загрузка

Допустим, игрок перемещается по городу.

Алгоритм:

1. Определяем текущий чанк игрока.
2. Вычисляем область видимости и загрузки вокруг него.
3. Получаем список необходимых чанков из `chunk-index.json`.
4. Загружаем данные соответствующих чанков.
5. Разрешаем ссылки на глобальные сущности.
6. Загружаем нужные ресурсы из Asset Library.
7. Регистрируем геометрию, фрагменты дорог, рек и рельефа.
8. Соединяем граничные Portal.
9. Загружаем коллизии и навигацию.
10. Выгружаем чанки, которые больше не нужны.

Полезно разделить радиусы:

| Область           | Назначение             |
| ----------------- | ---------------------- |
| Load radius       | Полная загрузка данных |
| Render radius     | Отображение            |
| Simulation radius | Работа игровой логики  |
| Unload radius     | Удаление из памяти     |

Например, можно начать с загрузки чанков в радиусе 2–3 ячеек вокруг игрока, но конкретные значения зависят от скорости перемещения и размера города.

Также понадобится асинхронная загрузка, чтобы игрок не останавливался при переходе между чанками.

## 11. Моя итоговая рекомендация для CityForge

Я бы добавил в формат пять новых понятий:

| Сущность           | Назначение                                      |
| ------------------ | ----------------------------------------------- |
| `Chunk`            | Пространственная единица хранения               |
| `ChunkIndex`       | Индекс и метаданные чанков                      |
| `EntityRef`        | Ссылка на глобальную сущность                   |
| `GeometryFragment` | Геометрическая часть объекта в конкретном чанке |
| `Portal`           | Соединение фрагментов на границах чанков        |

И установил бы следующие архитектурные правила:

1. Глобальный ID. Любая логическая сущность имеет уникальный идентификатор, не зависящий от чанка.
2. Один владелец. У каждой сущности есть один `homeChunk`, если она вообще имеет владельца.
3. Много областей покрытия. Сущность может встречаться в пространственном индексе нескольких чанков.
4. Геометрическое разбиение. Длинные объекты разбиваются на `GeometryFragment`, но сохраняют общий ID исходной сущности.
5. Согласованные границы. Все фрагменты используют идентичные координаты точек соединения.
6. Независимая загрузка. Чанк можно загрузить и выгрузить, не разрушая логическую модель соседних чанков.

## Итоговая схема

Global Entity

Road 001 / River 001 / House 001

Spatial partitioning

Chunk 0

Fragment 0

Chunk 1

Fragment 1

Chunk 2

Fragment 2

Фрагменты имеют собственные данные, но ссылаются на одну логическую сущность.

Самое важное решение: не делай Chunk частью иерархии города наравне с районом или кварталом. Районы и кварталы описывают смысловую структуру города, а чанки — исключительно способ пространственного хранения и загрузки.

Так одна и та же модель CityForge сможет обслуживать редактор города, процедурный генератор, серверную симуляцию и игровой движок, не создавая четыре разных представления города.
