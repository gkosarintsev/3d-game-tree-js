# План: пять дефектов из журнала владельца (2026-11-03)

Замеры сняты до правок; каждое решение ниже — с числом, которое оно должен снять.
Коммиты идут по одному на пункт журнала, порядок — от движка к данным.

## 1. Перевал Чужого: ось вращения (главы 9–11, любой дом)

**Замер.** Всю ориентацию перехода задаёт один кватернион
`_beginTransition` → `this._twQ.setFromUnitVectors(this._twFromUp, this._twToUp)`
(`src/alien.js:601`). Ни касательной кромки, ни направления бега в нём нет.

- Потолок → кровля: `fromUp = (0,−1,0)`, `toUp = (0,1,0)` — антипараллельны.
  Three.js при `r < ε` берёт ось из наименьшей по модулю компоненты: для `(0,−1,0)`
  это `(0,0,−1)`, то есть **вдоль оси Z мира**, а не относительно бега. Если Чужой
  идёт по X — ось случайно верна; если по Z (настилы моста 11-й главы) — она
  параллельна взгляду, и тело делает бочку вокруг линии взгляда. Ровно то, что
  описано как «плоскость поворота перпендикулярна направлению взгляда».
- Стена → кровля: ось `fromUp × toUp` в порядке, но `fromUp` берут из
  сглаженного `this.up` (`_alignUp:107`), а цель принимается при любом
  `hit.ny ≥ 0.5` (`_tryMantle:313`). Наклонная нормаль косой фасада (дома
  `rotation` в v2!) наклоняет ось в XZ → рысканье во время тангажа. Второй
  источник «поворота вбок»: `_restoreLook` возвращает false, когда взгляд
  совпал с нормалью, и `_replanar` бросает `fwd` на мировые `(0,0,1)`/`(1,0,0)`
  (`src/alien.js:96-104`).

**Решение.** Переход строит **два кадра** (источник и цель), а не дугу между
нормалями:

- `travel` — горизонтальная проекция `_wish`, при вырождении — проекция `fwd`,
  при нём — горизонтальная часть `(toPos − fromPos)`.
- Цель: `u2 = normalize(hit.n)`, `f2 = normalize(travel − u2·(travel·u2))`.
  Рысканье цели задаёт направление подъёма, а не мировой ось.
- Источник: `u1 = this.up`, `f1 = this.fwd` как есть.
- Оба кадра → кватернионы через общий базис (он уже есть для меша: `up`/`fwd`),
  `slerp` между ними. Для wall→roof с точными нормалями это даёт тот же
  поворот на −90° вокруг касательной, что и сегодня, — документированный
  перенос взгляда (`src/alien.js:611-613`) сохраняется.
- Если `u1·u2 < −0.95` (горизонталь ↔ антипод: потолок → кровля сквозь люк),
  один `slerp` обязан быть бочкой, потому что конечная ориентация
  «головка та же, нормаль противоположная» математически и есть поворот на
  180° вокруг взгляда. Поэтому переход разбивается на **две фазы** через
  промежуточный кадр вертикальной стойки (`f = +Y`, `u = −travel`): два
  тангажа по 90° вокруг касательной кромки, суммарно — та же конечная
  ориентация, но плоскость вращения каждой фазы содержит направление бега.

**Тест.** `tests/alien-climb.test.js`: существующие проверки (`up.y`, позиции,
`flatTail`) не меняются; новые — ось перехода потолок→кровля перпендикулярна
мировой Z при беге вдоль Z (замер: `max |Δ(camera.up × travel)|` по кадрам) и
рысканье корпуса за wall→roof не больше порога (замер: `|Δyaw| ≤ 0,05 рад`).

**Как сделано.** Конечный кадр цели (`u2 = hit.n`, `f2` вдоль `travel`) оказался
лишним: он фиксировал ровно ту ориентацию, что и бочка. Реализация держит дугу
вокруг **касательной кромки** (`_transitionAxis`: обычно `fromUp × toUp`, при
антипараллельных нормах — `travel × toUp`, то есть голова в середине дуги
смотрит на новую опору, а не вниз), доводит её конец точно в `toUp` (`_twFix`,
иначе последний кадр разворачивает корпус рывком) и переносит линию взгляда
вместе с корпусом — `_replanar` на мировую ось больше не вызывается из середины
перехода. Для дуги, близкой к π (`arc > 0.75π`), добавлен второй этап: доворот вокруг `toUp`
на угол между «вперёд» после дуги и направлением бега (`_twTwistAng`), размазанный
по второй половине перехода. Без него перевал через люк оставляет курс против
бега, и с зажатой «вперёд» тело тут же возвращается в тот же лаз (замер на тесте
`testHoleSweepFollowsRun`: 150 кадров — 9 перевалов туда-обратно, `up.x` так и
не уходит с нуля, но `z` колеблется между −0.01 и 3.01).

**Прогон.** `tests/alien-climb.test.js` — 21/21 (было 19; добавлены
`testHoleSweepFollowsRun` и `testMantleKeepsHeading`), остальные сюиты не
двинулись: `alien-enemy` 5/5, `model-level` 24/24 (перевал `_tryMantle` по
макету), `terrain-traverse` 18/18, `city-level` 15/15, `night-lights` 7/7,
`stream-map` 11/11, `json-level` 49/49, `json2-level` 15/15, `rotated-solid`
10/10, `rotated-house` 12/12, `rotated-road` 11/11, `rotated-sweep` 12/12 —
**210/210**.

## 2. Крутые марши генератора (глава 10, `sind_183_r0`)

**Замер.** Лот `sind_183`: 11 × 11 м, `floorHeight 4.5`, комната с паддингом
9.5 × 9.5 м. `stairPlan` берёт `n = max(4, ⌈fh / J.maxRise⌉) = 9`
(`tools/city.js:741`, `J.maxRise = 0.55`) и `straightL = max(n·TREAD_MIN,
STAIR_DEPTH) = max(9·0.28, 1.9) = 2.52` (`:748`). Нормировщик делит высоту на
`n` и длину на `n` (`tools/normalize-level.mjs:401-435`) → rise 0.5, tread 0.28.

Уклон марша = `height / L` = 4.5 / 2.52 = **1.786 (60,7°)**. Предел Чужого
«круче этого — стена» `climbSlope = 1.3` (52°), `src/config.js:56`. Прямых
маршей с таким уклоном в авторских главах нет: `level-09` даёт 0.58/0.62/0.53,
`level-11` — 0.60/0.53. Плита перекрытия над шахтой прорезана корректно
(`src/json-map.js:446-462`), «упирается в потолок» — следствие уклона: тело
читает марш стеной и встаёт на `canClimb` вместо ходьбы.

**Решение.** Уклон марша становится ограничением раскладки, а не следствием
подбора проступей:

- `J.maxStairSlope = 0.8` (38,7°) в `src/config.js`, рядом с `J.maxRise`.
- Кандидат в `stairPlan` проходит, если его **беговая длина** `run(type, L, W)`
  даёт `fh / run ≤ J.maxStairSlope`: `straight` — `L`, `l_shape` —
  `0.6·L + 0.5·W` (по `stairLayout:410-414`), `spiral` — `2πR`. Прямой марш при
  этом вырастает до `L ≥ 4.5/0.8 = 5.63` м, плюс две посадки 2.6 м — влезает в
  9.5 м комнаты, то есть в `sind_183` тип не меняется, меняется длина.
- Не проходит ни один кандидат → тот же счётчик `house_no_stair`, молчания нет
  (правило AGENTS про отказ лота).
- Валидатор проверяет уклон марша из брифа по той же формуле — авторский крутой
  марш получает предупреждение, а не тихую картинку.

**Регенерация.** Порядок вызовов ГПСЧ в генераторе значим, поэтому
`level-10.js` пересобирается целиком и коммитится вместе с правкой; `--check`
обязан сходиться побайтно, предупреждений парсер не даёт.

**Тест.** `node tools/level-parser.test.mjs`: уклон каждого марша каждого
сгенерированного лота ≤ `J.maxStairSlope`, и в частности `sind_183` больше не
в списке крутых. Браузер: маршрут врага через марш `sind_183` достижим.

**Как сделано.** `J.maxStairSlope = 0.8` (`src/config.js`), `stairRun(type, L, W)`
экспортируется из `tools/normalize-level.mjs` и живёт в одном месте: по ней
`stairPlan` (`tools/city.js`) отсекает кандидатов до броска (`minRun = fh / 0.8`,
прямой — `straightL ≥ minRun`, Г-образный — `0.6·L + 0.5·W ≥ minRun`, винт —
`π·D ≥ minRun`), по ней же нормализатор пишет предупреждение авторскому крутому
маршу (`normalizeStair`, `ladder` не проверяется — у шахты подъём держит отметка
пластины, а не шаг). Отказ подобрать марш обязан стоить того же расхода ГПСЧ,
что и удачный подбор (три `rng()`), иначе снятие одного лота сдвигает счётчики
всех последующих районов и город перестраивается целиком.

Расширение кандидатов вскрывает другую ветку: беговая длина прямого марша
выросла с 2.52 до 4.375 м, его план съедает клетки решётки комнаты у стены, и
посадка остаётся без соседа-пола. `_refineFloor` вызывался по признаку
`nav.adj[land].length <= 1`, а `_linkClosest` охотно цепляет предпоследнюю
проступь — «два ребра, оба на лестнице», и этаж отрезался `_pruneToSpawn`
(`ncc_018`, этажи 2 и 3). Признак заменён на `_landingHasFloor`: у соседа
отметка уровня и его точка вне плана марша.

Вторая находка — посадка винта. `skit_260_s1`: первая проступь на дуге в
1,9 м от западной посадочной клетки, между ними — проём перекрытия, и
`_edgeSupported` бракует ребро «посадка → ступень» (на нулевом этаже то же ребро
живёт, потому что под шахтой держит грунт). `_landing` перебирает направления,
пока не найдётся пол и свобода; теперь он требует и того, что нога дотягивается
до своей проступи, и разворачивается на следующее направление (у винта — к краю,
к которому сектор ближе всего). Без этого правки генератора дали бы город, где
второй этаж дома существует только на картинке.

**Прогон.** Замер по `src/levels/level-10.js` (до правки → после): худший уклон
`ncc_018_s0` и `sind_183_s0` **1.786 → 0.800**, маршей круче лимита **63 → 0**
(из 99 и 117 соответственно). Состав маршей: прямой 74 → 42, Г-образный 5 → 3,
винт **3 → 57**, шахта кровли 17 → 15 — при комнате 6–7 м прямой марш требует
6.975 м (4.375 + две посадки) и не влезает, поэтому винт остаётся единственным
кандидатом; это заметная перемена подъездов, при желании ретунируется
порогом `d` в `stairPlan`. Счётчики разворота района: лотов 302 → 278,
вводимых 28 → 30, кровель 11 → 9, отказов `house_no_stair` 35 → 24.
`node tools/level-parser.test.mjs` — **99/99**; `--check` сходится побайтно для
глав 09, 10, 11, предупреждений парсера ноль. Браузер (порт 8190):
**211/211** — json-level 50/50 (включая новый «Марши города: у каждого конца
марша есть посадка, связанная с полом», «каждый этаж вводимого дома …
достижимы» и «глава 10: все вводимые дома открыты ногами»), city 15/15,
json2 15/15, rotated-house 12/12, rotated-road 11/11, rotated-sweep 12/12,

## 3. Люк кровли односторонний (глава 11, `be_roof`/`bw_roof`/`bwb_roof`)

**Замер.** Все проступи вертикального марша лежат **в одном плане** шахты
(`stairLayout('ladder')` → `full: true`, `normalize-level.mjs:397-399`),
различаются только отметкой верха, и верхняя приходит ровно на `roofY`
(правило в AGENTS). Для `be_roof`: `roofY 9.6`, `n = 6`, `risePer 0.5333`,
верхня 6.933…9.600.

`SolidField.groundHeightAt` (`src/solids.js:123-137`) отвечает **самую высокую**
опору не выше `feet + CONFIG.building.stepUp (0.6)`. Стоя на кровле над люком
(`feet 9.6`, предел `10.2`), спрашивающий получает 9.6 — своя же верхняя
проступь, заподлицо с кровлей. Провала нет, спускаться некуда: марш
односторонний по построению. Подъём работает, потому что снизу каждая ступень
в пределах 0.533 ≤ 0.6.

**Решение (по выбору владельца — менять правило, а не добавлять climb-стейт).**
Верхняя проступь вертикального марша останавливается на **одном rise ниже**
своей отметки назначения:

- `stairLayout` для `type === 'ladder'` даёт `risePer = height / ⌈height /
  J.maxRise⌉` и пластин на одну меньше (`count = n − 1`), верхняя — на
  `y1 − risePer` (то есть подъёмов ровно столько, сколько нужно, и последний
  остаётся между верхней пластиной и этажом или кровлей).
- Проём в плите кровли остаётся полным планом шахты: голова того, кто на
  последней проступи (9.067 + 1,7 = 10.77) проходит сквозь плиту `[9.3, 9.6]`
  только благодаря прорезу.
- Тогда и вверх, и вниз: с последней проступи на плиту кровли +0.533 ≤ 0.6,
  с плиты кровли в люк −0.533. Дыра читается опорой в обе стороны.
- Правило в AGENTS.md («верхняя приходит ровно на y1 или roofY») и
  `docs/architecture-json-levels.md` переформулируются: верхняя пластина — на
  один подъём ниже своей отметки (этажа или кровли), а не ровно на ней.
- Полоса кровли у края люка: у `be_roof` шахта 1.4 м в углу, до фасада 0.625 м
  (узко для радиуса 0.45), но `_landing` уже выбирает открытую сторону (`+z`),
  там 11.8 м кровли — посадка есть.

**Регенерация:** меняется нормировщик → пересобираются `level-10.js` и
`level-11.js` (в `level-09.js` вертикальных маршей нет, его байты не двинулись).

**Тест.** Node: у любого вертикального марша `steps.length = ⌈height /
J.maxRise⌉ − 1`, верхняя пластина — на `risePer` ниже `y1`, и этот зазор ≤
`CONFIG.building.stepUp`. Браузер (`tests/json2-level.test.js`): над шахтой
`groundHeightAt` отвечает верхнюю пластину, а не плиту кровли, шаг с плиты в люк
перешагиваем, подъём по проступям цел, под шахтой — пол этажа.

**Как сделано.** Правило оказалось шире люка: тот же самый план проступи лишает
спуска и **межэтажный** вертикальный марш (плита этажа над шахтой заподлицо с
верхней пластиной — дыры с этажа тоже нет). Поэтому зазор в один подъём сделан
для **всех** `ladder`, а не только для `k1 === floorsCount`: `stairLayout` для
`ladder` даёт `risePer = height / ⌈height / J.maxRise⌉` и `count = n − 1`
пластин, верхняя — на `y1 − risePer` (этаж или кровля — не разбирая). Число
пластин на единицу меньше, чем подъёмов, `Math.max(3, …)` держит минимум две.

Остаток, который правило не убирает (и не может, пока у марша один план и нет
climb-стейта): внутри шахты `groundHeightAt` всегда отвечает пластину не ниже
той, на которой стоишь, — по проступям вниз не идти. Спуск через люк теперь
кончается падением от верхней пластины до пола этажа (`be_roof` 2,6 м, `bw_roof`
3,1 м — замер в `info` нового браузерного теста). Ловушкой кровля при этом быть
перестаёт: её край держит парапет, и раньше с кровли не было выхода вообще, а
теперь люк держит вход.

Побочный потребитель абстракции — **мусор кровель** (`_clutterItems`): сетка
слотов не сверялась с опорой и ставила бак поверх фантомной пластины, лежавшей
заподлицо с плитой. Автотест «мусор стоит на своей опоре» поймал это сразу после
правки: предмет на кровле `nkab_086` (глава 10) встал над шахтой `nkab_086_roof`
и оказался в 0,5 м над своей опорой. Слот теперь бракуется
`_inStair(b, x, z, floorsCount)` — предмет не закрывает проём и не висит над
ним.

**Прогон.** Node 99/99 (`--check` у 09/10/11 сходится байт-в-байт, 0
предупреждений; все 15 вертикальных маршей главы 10 выведены в люк — у каждого
снята верхняя пластина, 120 строк модуля; в главе 11 таких маршей 3, 24 строки).
Браузер: json-level 50/50 (правил свои две проверки —
«проём марша в плите кровли» и «вертикальный марш поднимает нога»), city 15/15,
json2 16/16 (новая — «Люк кровли: над шахтой плита не опора, с кровли сойти
можно, подъём цел»: 3 люка, шаг с плиты в люк 0,533 м), rotated-house 12/12,
rotated-road 11/11, rotated-sweep 12/12, rotated-solid 10/10, terrain 18/18,

## 4. Стык креновой дуги, перила и съезд (глава 11, `rd_interchange`)

**Замер.**

- Несовпадение линии стыка дуги с настилом — **крен**, а не пластины.
  `bank 6°` → `tanBank 0.1051`, `halfW 4` → край ±0.4204 м относительно оси
  (`normalizeArc:583-605`). На торце дуги (z 58…66) срез даёт 11.58 и 12.42,
  настил `plate y 12` плоский: контакт — диагональ 0.84 м на 8 м ширины.
- Перила (`_sweepRails:618-636`) есть **только у дуг**: поле `rails` разрешено
  схемой лишь в `V2_ARC` (`level-schema.mjs:240`), у `V2_PLATE` (`:216-224`)
  его нет → у 94-метрового настила и у съезда ограждений нет вовсе.
  Сама перила — лесенка из `n = ⌈3.8167·40/2⌉ = 76` коробок (хорда 2.01 м,
  +0.158 м каждая), и низ/верх секции считаются **по осевой** (`sweepSurfaceAt(s, a, s.R)`),
  а стоит секция на `ρ = R ± halfW` → у внутреннего края основание висит 0.42 м
  над настилом, у внешнего утоплено на 0.42.
- Съезд `plate {x:−64, z:62, length:40, y:12, rise:−11.88}` (yaw 180 от
  `connect:'tangent'`) даёт верх 12 при x = −44 и 0.12 при x = −84 — с
  `rd_west_stub` (0.12) стык совпадает ровно. Не совпадает другое: у
  элементных дорог `fill/aprons/pillars/lamps = []`
  (`normalize-level.mjs:738-741`), то есть под наклоном нет ни насыпи, ни
  опор. Нижняя грань пластины наклонена параллельно верхней (призма-
  параллелограмм в профиле, `_incline:649-662`), поэтому видимая граница
  «съезд ↔ земля» — диагональ, а нос пластины кончается вертикальной
  стеной 0.12 над грунтом.

**Решение — три коммита (4a, 4b, 4c), каждый зелёный.**

**4a. Переходный крен.** Кен — функция угла, а не константа секции: он ноль на
обоих торцах дуги, примыкающих к прямым элементам, и разгоняется до авторского
`bank` по косинусоиде за длину `L_t = π/2 · tanBank·halfW / J.maxSlope`
(0.42·1.57/0.3 = 2.2 м, клампится в 40 % развёртки на конец). Это держит
продольный уклон **края** полотна в том же `J.maxSlope`, которым схема ограничена
ось, и делает линию стыка горизонталью. Все потребители берут одну функцию
`bankAt(d, ang)`: `arcTopAt`, `topAt`/`sweepTopAt`/`sweepSurfaceAt`, `_sweepMesh`
(кольца уже идут по нарезке), `raySolid`, `resolveSphere`, и `topAtMin/topAtMax`
валидатора — последние становятся отметками **срезов** (без крена), поэтому
проверка моста над рекой перестаёт видеть ложный гребень.

**4b. Гладкие перила.** Перила — стенка как продолжение полотна, а не коробки:

- Дуга: аналитическая цилиндрическая стенка `ρ = R ± halfW` от фактической
  высоты края до `+ J.railHeight` (луч решается как `|p − c| = ρ`, сфера
  выталкивается радиально — той же формулой, что держит опору дуги сегодня).
- Пластина/съезд: перила — **призма** (`prisms`) с профилем
  `[(u_lo, top), (u_hi, top), (u_hi, top + railHeight), (u_lo, top + railHeight)]`
  по каждой кромке; у пластины нет поперечного уклона, поэтому верх профиля —
  горизонтальная линия, и опора/луч/сфера уже работают по призме без нового
  механизма.
- Поле `rails` переезжает в `V2_PLATE` (`level-schema.mjs:216-224`) и в
  `normalizeRoadElements`, `_sweepRails` из коробок удаляется вместе с
  `J.railStep`. Перила остаются **блокерами края** для графа (узлы идут по
  осевой — правило не меняется), но не солидами во всю высоту прохода.

**4c. Насыпь под съездом.** Для наклонных элементов выдавать `fill` — призму с
треугольным профилем между нижней гранью настила и уровнем грунта: там, где
низ пластины ниже `ground.y` (у носка съезда −0.48), граница призмы идёт по
`ground.y − J.seam` и становится **горизонтальной линией**, выше — по низу
настила. Ника нового представления не нужно: профиль выпуклый, механизм призм
тот же, что у откоса насыпи.

**Тест.** `tests/rotated-sweep.test.js` / `rotated-road.test.js`: линия стыка дуги
и настила горизонтальна (замер: разность высот края среза и `plate.y` = 0),
основание перил лежит на краю полотна (замер был ±0.42), у съезда нет висящего
объёма под настилом, перила пластины бракуют край графа, но не осевую.

## 5. Косой вводимый дом в данных (глава 11)

**Замер.** Схема и `JsonMap` это умеют сегодня: `rotation` — в `LEVEL_SPEC_V2`
(`level-schema.mjs:267-273`), `isEnterable` — `:86`, координаты footprint,
комнат, марша и портала остаются **в локальных осях** дома, кадр поворота
восстанавливает `JsonMap` (`src/json-map.js:163-233`), дверь поворачивает
`inside/outside` в нормировщике (`normalize-level.mjs:192-225`). Готовый
образец — `probe/v2-house.json` (rotation 30, лобби + склад + офис, `straight`
марш, `ladder` на ходовую кровлю), покрыт 12 сценариями
`tests/rotated-house.test.js`. В 11-й главе оба косых дома помечены
`isEnterable: false` — то есть нет только данных.

Ограничения, которые надо учесть при авторстве: косой дом **не держит**
skybridge и настил (`level-schema.mjs:696-700, 715-733`,
`src/json-map.js:325` — `arrivals = frame ? [] : ...`), `stairs[].rotation`
кратен 90° (`normalize-level.mjs:356`), пересекаться могут только дома с одним
`rotation` (`:655-667`), план обязан уйти от улицы и русла (`:530-545`).

**Решение.** `house_yaw30` (локальный rect −97…−79 × 72…84, yaw 30) становится
вводимым: комната-лобби на 0 этаже с дверью на улицу, комната на 1, `straight`
марш между ними, `ladder` на ходовую кровлю с парапетом. Портал подбирается так,
чтобы `outside` после поворота лёг на план `rd_west_cross_n` (z = 50) — при
необходимости западный отрезок удлиняется, косой дом к настилу не крепится.
Проверяется браузером: граф через косой дом, обе лестницы, жилые узлы внутри и
на кровле, маршрут A→B не разорван; `tools/build-level.mjs` без предупреждений.
